01
UAT approach
Who tested this, and why that has to be stated plainly
This is a self-directed case study — there's no separate business stakeholder to hand this off to for acceptance testing. Every test below was designed and run by the same person who built L0–L5, wearing both the "builder" and "acceptance reviewer" hat. That's a real limitation on independence, and it's stated here directly rather than implied away by formal-sounding UAT language.
To keep that limitation from becoming an excuse for weak testing, the test cases below are restricted to claims that can be checked two ways: against a code comment or label already embedded in L2–L4 at build time, and against a fresh recalculation done while writing this page. A test only counts as run if both checks agree.
What this UAT is not
Not a full regression suite, not independent QA, not a claim that every corner of L0–L5 was tested. It's a re-verification of the specific numeric and behavioral claims those layers made, using evidence that already exists in the code and output — nothing was tested that isn't traceable to something built.

05
Project closure & retrospective
Where this landed against the original Gate 1 target, and what each layer was actually for
The original Gate 1 target was L0–L2 complete plus a first wave of job applications sent by 31 August 2026. All seven layers — L0 through L6 — are complete ahead of that date, which is worth stating plainly without overselling it: the extra layers exist because the case study kept surfacing real BA/BSA-relevant questions (governance, ROI honesty, acceptance testing) worth answering, not because the original scope required it.
layerwhat it actually proved
L0Understanding the business problem before touching a tool
L1Designing a process on paper before writing a query
L2Turning business rules into verified SQL — and catching a real branch-order bug along the way
L3Communicating findings through a dashboard, and treating a tooling pivot (static HTML over Power BI publish) as a deliberate choice, not a failure
L4Deciding where AI belongs in a workflow, and designing a system where it structurally can't overstep that boundary
L5Separating what's measured from what's assumed in a business case, instead of blending them into one impressive number
L6Applying that same honesty to testing itself — six real checks beat thirty invented ones
Closed. This case study set out to show how a Business Analyst redesigns a financial review process end-to-end — discovery through UAT — on public data, with every claim either verified or explicitly labeled as an assumption. L6 is the layer that checks whether that discipline actually held up, and it did.
★
Lesson: The same instinct that made L5's R$199.52 more credible than R$271,891.01 applies to testing — a short, honest test matrix that's actually traceable to the code beats a long one that isn't. In an interview, "here are the six things I checked and how" holds up to follow-up questions in a way a padded list doesn't.
